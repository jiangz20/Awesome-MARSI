# MARSI 阅读与研究指南

## 建议阅读顺序

| 路径 | 推荐论文 | 重点问题 |
|---|---|---|
| 直接相关 | [MASS 2026](https://arxiv.org/abs/2610.12176)、[Gödel Forest](https://arxiv.org/abs/2609.36675)、[RHI](https://arxiv.org/abs/2607.15524)、[MAE](https://arxiv.org/abs/2510.23595) | 谁生成候选、谁执行、谁评价？更新后哪一部分进入下一轮？ |

## 阅读矩阵

以下是本仓库的阅读框架，不是公认的 RSI 分级标准，也不是对论文优劣的排名。

| 机制 | 被修改的对象 | 需要检查的证据 |
|---|---|---|
| 单次输出优化 | 当前答案、推理轨迹 | 改进是否只存在于当前问题？ |
| 系统优化 | 提示、拓扑、工具、运行代码 | 修改是否在后续任务中持续存在？ |
| 经验继承 | 记忆、技能、搜索档案 | 清空经验后增益是否消失？未见任务是否受益？ |
| 参数适应 | 执行、出题或评价模型权重 | 哪些角色被更新？监督从何而来？是否发生能力退化？ |
| 递归改进 | 也承担改进职责的组件 | 新一代是否在同起点、同预算下更会改进系统？ |

模型不更新权重也可能实现有意义的递归改进；更新权重也不自动证明递归改进。多角色不一定意味着多个独立基模；种群搜索也不一定包含任务内协作。

## 建议记录的实验信息

以下是整理文献时的建议，而非上述论文都已经完成的实验。

1. **更新闭环**：候选生成、执行、反馈、接受、继承分别由谁实现；评价器是否同时变化。
2. **数据边界**：训练、候选选择、最终测试和跨域迁移如何隔离；开发反馈是否触及最终测试。
3. **预算**：计入全部 agent 的 token、工具调用、失败候选、训练及选择成本；同时报告并行耗时与总成本。
4. **对照**：单 agent、固定多 agent、独立并行搜索、无共享经验、固定改进器、完整系统。
5. **递归证据**：让不同代改进器从相同执行系统出发，在相同预算下生成候选，再用独立测试比较。
6. **稳定性**：报告最后一代与开发集选择的最佳一代，观察退化、回滚和跨域保留；不能用测试集挑最佳代。

基础 benchmark 只能提供任务成绩锚点。是否支持 MARSI 主张，还取决于跨轮协议、成本匹配、反馈隔离和消融设计。
